# Miku Repository Review — 2026-07

A full audit of the `miku` IM server (C99-C23, CMake). Findings are grouped by
severity with exact file:line references. The remediation plan prioritises
correctness first (the test harness was silently swallowing failures), then
memory safety, then performance, then CI hardening.

## Executive Summary

The project builds cleanly (`-Wall -Wextra -Wpedantic -Wconversion`, 0 warnings)
and ships 13 binaries. However the test framework had a defect that caused
**every test suite run to exit 0 regardless of failures**, which masked three
real functional bugs and let memory-safety regressions ship undetected. ASAN
surfaced a dangling-pointer API bug, undefined behaviour in the protobuf
encoder, and unchecked allocations in the HTTP server.

After remediation all 195 tests pass under both Debug and ASAN builds.

## Critical Findings

### C1. Test harness reports success on failure (silent green CI)
- `tests/miku_test.h:105` `mk_run_test` unconditionally runs `mk_tests_passed++`
  and prints `OK`. The `if (... || 1)` block is dead code.
- `mk_tests_failed` is never incremented, so `mk_test_summary` always returns 0.
- Effect: CI's `timeout 60 ./build/bin/miku_tests` step is always green.
  Three actually-failing tests were hidden:
  - `test_msg_pull_by_seq_range` (`tests/test_new_modules.c:1272`)
  - `test_group_member_sync_callback` (`tests/test_new_modules.c:2562`)
  - `test_admin_stats` (`tests/test_new_modules.c:3156`)

### C2. `miku_error_msg` returns a dangling pointer
- `src/foundation/miku_error.c:31` takes `miku_error_t` **by value** and returns
  `err.msg`, which points into the by-value copy's now-dead stack frame.
- ASAN: `stack-use-after-return` in `test_error` (`tests/test_foundation.c:119`).
- The struct is 260 bytes (`int` + `char[256]`), so pass-by-value is also
  needlessly expensive.

### C3. Undefined behaviour in protobuf svarint encoder
- `src/protocol/miku_pb.c:71` `(val << 1)` where `val` is `int64_t` and may be
  negative — left-shifting a negative signed value is UB in C.
- ASAN/UBSan: `left shift of negative value -1`.

### C4. Unchecked allocations in HTTP server
- `src/protocol/miku_http_server.c:86-87` `realloc` results are assigned
  directly to `srv->conn_fds` / `srv->conn_last_active`; on failure the original
  pointer is leaked, `conn_cap` is bumped anyway, and the next access
  dereferences NULL. Also a `realloc`-on-failure leak.
- `src/protocol/miku_http_server.c:405-406` `malloc` results unchecked.

### C5. `sendBusinessNotification` double-gate defeats admin bypass
- `src/services/msg/miku_msg.c:632` computes its own `gate` then calls
  `miku_msg_send`, which re-runs `msg_send_gate` (`miku_msg.c:196`). The admin
  bypass (`gate = 0`) is therefore discarded and admin direct notifications hit
  `6002 not mutual friends`.
- `send` (`miku_msg.c:602`) and `sendSimpleMsg` (`miku_msg.c:619`) have the same
  double-gate pattern — a redundant O(1) but unnecessary cost on the send hot
  path, and a latent correctness trap.
- API layer (`src/gateway/api/miku_api.c:1211`) rejects all non-admin
  `sendBusinessNotification` with 403, but group-targeted notifications are
  expected to be gated by group membership (3003) instead.

## High Findings

### H1. `pullMsgBySeq` omits `data` on the validation-error path
- `src/services/msg/miku_msg.c:688` `break`s before setting `data`, so the
  response has no `data` field. Callers expecting a (possibly empty) `data`
  array get NULL.

### H2. Test helper `make_req` stack-use-after-return
- `tests/test_protocol.c:766` parses into a local `char buf[4096]`; the parsed
  request's `path.data` aliases `buf`, which dies on return. ASAN flags
  `path_equals` (`src/protocol/miku_middleware.c:68`). Same issue in
  `make_req_with_token` (`tests/test_protocol.c:779`).

### H3. Memory leaks surfaced by ASAN
- LeakSanitizer reports a ~168 MB single allocation plus ~28 MB across millions
  of small objects during a full test run. Most originate in test fixtures that
  allocate JSON/services without teardown. Not addressed in this pass (tracked
  below); the correctness fixes above take precedence.

## Medium Findings

### M1. CI has no ASAN/UBSan job and no caching
- `.github/workflows/ci.yml` runs only a Debug build + test. No sanitizer job,
  no `ccache`, no release build verification. C2/C3 above would have been caught
  by a sanitizer job.

### M2. CI test step cannot detect failure
- Even with C1 fixed at the harness level, the CI `Test` step relies on the
  process exit code. This is now correct once C1 is fixed, but worth noting.

### M3. `march=native` in the default Release flags
- `CMakeLists.txt:61` uses `-march=native`, which produces non-portable binaries
  (e.g. AVX-only instructions). Fine for local builds; risky for distributed
  release artifacts. Left as-is (no release artifact pipeline exists yet).

## Low Findings

### L1. README stat drift
- README claims 171 tests / ~15K LOC; actual is 195 `mk_run_test` calls and
  18,254 LOC (15,534 `.c` + headers). Cosmetic.

### L2. No `.dockerignore`
- `Dockerfile` `COPY . .` ships `build/`, `build-asan/`, `.git/`, `notes.html`
  (70 KB), `ARCHITECTURE.md` (62 KB) into the build context, inflating context
  and layer cache churn.

## Remediation Plan (performance-optimal ordering)

The ordering below front-loads the change that unblocks all other verification,
then memory safety, then the perf-aligned correctness fixes.

1. **Test harness** (`tests/miku_test.h`): track failures via a per-test flag
   set before each assertion's `return`; `mk_run_test` inspects it to bump
   `mk_tests_failed` instead of unconditionally bumping `mk_tests_passed`.
   `mk_test_summary` exit code now reflects reality.
2. **`miku_error_msg`** (`miku_error.h`, `miku_error.c`): take
   `const miku_error_t *` and return `err->msg`. Update the single caller.
   Removes the dangling pointer and the 260-byte by-value copy.
3. **`miku_pb.c` svarint**: cast to `uint64_t` before the left shift.
4. **HTTP server allocs** (`miku_http_server.c`): check `malloc`/`realloc`
   returns; on `realloc` failure preserve the old pointer and abort the grow.
5. **`pullMsgBySeq`** (`miku_msg.c`): always attach a `data` array (empty on
   the validation-error path).
6. **`sendBusinessNotification`** (`miku_msg.c`, `miku_api.c`): extract
   `msg_store_internal` (store without gate) so `miku_msg_send` gates once and
   the RPC handlers stop double-gating. New gate logic:
   group-targeted → `msg_send_gate` (3003 on non-member, applies to all);
   admin direct → presence check only (bypass friend check);
   non-admin direct → 403 (API layer). API layer relaxes the admin requirement
   only when `groupID` is present.
7. **Test helpers** (`tests/test_protocol.c`): make the parse buffer `static` so
   `path.data` stays valid for the request's lifetime (sequential test use).
8. **CI** (`.github/workflows/ci.yml`): add an `asan` job running the ASAN/UBSan
   build, and make the test step explicitly fail on non-zero exit.
9. **Docs**: refresh README stats; this review doc is the changelog of record.

## Second Pass (deeper audit)

A second pass verified the first-pass fixes held (195/195, ASAN-error-clean)
and dug into the items the first pass deferred: the ASAN leak report, hot-path
allocations, and test-coverage gaps.

### Findings

**SP1. Production per-response leak (CRITICAL).** `miku_http_response_set_json`
(`src/protocol/miku_http.c:100`) called `miku_hashmap_put(resp->headers,
strdup("Content-Type"), strdup("application/json"))`. The hashmap owns its keys
(`strdup`s them internally at `miku_hashmap.c:98`) and frees values via
`val_free=free`. Passing a `strdup`'d key therefore leaked the caller's copy on
**every JSON response** — an unbounded leak in any deployed `miku-api` /
`miku-msggateway`. The CORS middleware (`miku_middleware.c:17-19`) already used
the correct pattern (literal key, `strdup`'d value), confirming the intent.

**SP2. Benchmark destructor leaks (HIGH volume, test-only).** `bench_hashmap`
and `bench_cache` (`tests/test_benchmark.c:52,69`) created their containers with
`NULL` value destructors then inserted `strdup`'d values — leaking every
iteration. These were the dominant volume in the ASAN leak report (machine-
dependent; the earlier "168 MB single allocation" was this benchmark loop under
load, not an arena/slab/store leak).

**SP3. Threadpool per-task malloc (noted, not fixed).** `tq_push`
(`src/runtime/miku_threadpool.c:27`) `malloc`s a task struct per submit and the
worker `free`s it unlocked after run (`miku_threadpool.c:72`). The scheduler
submits a task on every coroutine resumption (`miku_scheduler.c:113`), so this
is on the hot path. However the struct is ~24 bytes (glibc tcache-fast), and a
freelist would either need an extra lock acquire per task (negating the win) or
lock-free code (real concurrency risk). Win/risk not clearly favorable; left
as-is and documented.

**SP4. Weak RPC dispatch smoke tests (noted, not fixed).** `test_new_modules.c:806`
enumerates RPC method names but only asserts "not 404" — it does not validate
method-specific results. Strengthening these is coverage work (not performance)
and is deferred.

**SP5. `test_new_modules` RPC fixture leaks (noted, not fixed).** The RPC
dispatch fixture creates request/response JSON per method without destroying
them. Test-only; CI runs ASAN with `detect_leaks=0`, so this is local-dev
cosmetic noise. Deferred (extensive, low value).

### Remediation (performance-optimal)

1. **SP1**: pass `"Content-Type"` (literal) as the hashmap key; keep the
   `strdup`'d value. Eliminates the unbounded production leak.
2. **SP2**: pass `free` as the value destructor in both benchmark containers.
   Removes the dominant ASAN leak volume so future real leaks are visible.
3. **L2** (from pass 1): add `.dockerignore` so `COPY . .` no longer ships
   `build/`, `.git/`, `notes.html`, etc. into the build context.

SP3/SP4/SP5 are documented above as deliberate deferrals with rationale.

### Verification (second pass)

- `cmake --build build -j$(nproc)` — 0 warnings, 0 errors.
- `./build/bin/miku_tests` — 195/195 pass, exit 0.
- `./build-asan/bin/miku_tests` (`detect_leaks=0`) — 195/195 pass, no ASAN/UBSan
  errors. With `detect_leaks=1`, the SP1/SP2 leak volume is gone; only the
  deferred SP5 test-fixture noise remains.

## Third Pass (performance + leak elimination)

A third pass closed the deferred leak debt (SP5) and targeted the throughput
hotspots the first two passes only noted. The headline result: the ASAN test
run went from **103 464 bytes / 1 634 allocations leaked** to **zero leaks**,
and two production hot paths were optimised.

### Findings

**TP1. Systemic `out` JSON leak across all API handlers (CRITICAL).** Every
handler in `src/gateway/api/miku_api.c` (`handle_auth`, `handle_user`,
`handle_friend`, `handle_group`, `handle_conv`, `handle_msg`) allocates the
response object `out = miku_json_create_object()` near entry, then has
`require_fields` / manual validation early-returns of the form
`miku_json_destroy(j); return;` that destroy the parsed body `j` but **not**
`out`. Every malformed request (missing required fields) therefore leaks one
JSON object — unbounded in any deployed `miku-api`. 25 leaking return paths
across 6 handlers. This is distinct from SP1 (the Content-Type key leak); it is
a larger, per-validation-error leak.

**TP2. Three unchecked `realloc` calls (correctness).** Same class as the
first-pass C4 fix, in code the first pass did not reach:
- `src/runtime/miku_scheduler.c:58` — `sched->coros = realloc(...)` with no
  NULL check; on failure the old pointer is lost and the next write is UB.
- `src/protocol/miku_json.c:191` — array parser `realloc` unchecked (the
  builder path at `:421` was already checked; the parser was not).
- `src/protocol/miku_json.c:229` — object parser `realloc` unchecked (same
  asymmetry; builder at `:439` was checked).

**TP3. Per-request 64 KiB heap allocation (performance).**
`miku_http_server.c:178` (`handle_client`) malloced `READ_BUF` (65 536 bytes)
for every readable client event, even though the common request (headers +
small JSON body) fits in a single 8 KiB `READ_CHUNK` read. On a high-RPS
gateway this is needless cache pressure and arena churn.

**TP4. RPC server handles one connection per poll (performance).**
`miku_rpc_server_poll` accepted a single connection per call, then did blocking
header/payload reads and response write before returning. All 7 production RPC
binaries (`miku-rpc-auth/user/friend/group/conv/msg/third`) run
`while (running) { miku_rpc_server_poll(srv, 100); }`, so under a burst of
concurrent RPCs the throughput was capped at roughly 10 req/s (one per 100 ms
poll). The listen backlog is 64, so up to 63 connections sat queued.

**TP5. Remaining test-fixture leaks (SP5 closure).** The deferred SP5 leaks
plus three additional sites:
- `tests/test_new_modules.c:794-796` — `test_dispatch_no_404_helper` (the SP5
  site; 22 methods × 6 services).
- `tests/test_protocol.c:892-893` — `test_api_route_handler_responds` leaked
  inline `miku_json_parse_str("{}")` and `miku_json_create_object()` args.
- `tests/test_protocol.c:413` — `test_json_get_missing` leaked
  `miku_json_create_null()`.

### Remediation (performance-optimal)

1. **TP1**: `miku_json_destroy(j); return;` → `miku_json_destroy(j);
   miku_json_destroy(out); return;` across all 25 sites in `miku_api.c`
   (6 handlers). Mechanical, uniform, no control-flow change.
2. **TP2**: each unchecked `realloc` now uses a temp pointer, checks for NULL,
   preserves the old buffer on failure, and returns an error (scheduler
   destroys the coro and returns NULL; JSON parser destroys `v`/`item`/`key`
   and returns NULL — matching the existing parser error contract).
3. **TP3**: introduced `READ_INIT (READ_CHUNK * 2)` = 16 KiB as the initial
   per-request buffer. Still fits a typical first read (8 KiB chunk + slack)
   without triggering a grow, but quarters the per-request allocation. Larger
   bodies grow via the existing realloc path up to `max_body`.
4. **TP4**: extracted `handle_one_connection` and changed `miku_rpc_server_poll`
   to drain the accept queue up to 64 connections per call (matching the listen
   backlog). Each accepted connection is still handled synchronously (the
   blocking-read model is unchanged — a non-blocking/epoll refactor is a
   separate, larger scope), but a burst is no longer serialised at one-per-poll.
5. **TP5**: added the missing `miku_json_destroy` calls in the three test sites.

### Deliberate deferrals (carried forward)

- **SP3** (threadpool per-task `malloc`): the ~24-byte task struct is tcache-
  fast; a freelist would need a lock-free MPSC or an extra lock acquire that
  negates the win. Unchanged.
- **Scheduler `ready_entry_t` per-wakeup `malloc`** (`miku_scheduler.c:70`):
  same shape as SP3; the scheduler is not on the production request path (HTTP
  and RPC servers use direct epoll). Unchanged.
- **RPC blocking-read model** (`miku_rpc_server.c`): a slow client still blocks
  its connection's read. A full epoll/non-blocking refactor is tracked but out
  of scope for this pass; the accept-queue drain (TP4) removes the worst cliff.

### Verification (third pass)

- `cmake --build build -j$(nproc)` — 0 warnings (`-Wall -Wextra -Wpedantic
  -Wconversion -Wshadow -Wstrict-prototypes -Wmissing-prototypes`), 0 errors.
- `./build/bin/miku_tests` — 195/195 pass, exit 0.
- `ASAN_OPTIONS=detect_leaks=1 ./build-asan/bin/miku_tests` — 195/195 pass,
  exit 0, **zero leaks**, zero ASAN/UBSan runtime errors.

## Fourth Pass (hot-path CPU + RPC robustness)

The third pass closed the leak debt. This pass targeted CPU waste on the two
production request hot paths (API gateway and WebSocket gateway) and fixed a
correctness defect in the RPC server's I/O handling.

### Findings

**FP1. Quadruple token verification per request (HIGH CPU).** Four functions
independently extracted and cryptographically verified the same bearer token:
`check_ratelimit` (`miku_api.c` old :308), `verify_token` (:387),
`req_token_uid` (:407), and `req_token_platform` (:419 — called up to 19×
across handler bodies). Each call runs the full HMAC-SHA256 verify path.
A single authenticated request therefore burned **4× the crypto cost**.

**FP2. WebSocket message parse→stringify→re-parse (HIGH CPU).**
`read_client_frames` (`miku_msggateway.c:538`) parsed the JSON envelope,
extracted the `data` subtree, **stringified it back to a string**, passed the
string to the `on_op` callback, and each handler case then **re-parsed** it.
Every WS message on the real-time gateway paid for one redundant stringify +
one redundant parse.

**FP3. RPC short-read and partial-write defects (CORRECTNESS).**
`handle_one_connection` called `read(fd, hdr_buf, 16)` and `read(fd, len_buf,
4)` assuming TCP returns the requested byte count in one call. TCP does not
preserve message boundaries; a short successful read was treated as a malformed
request, rejecting valid RPCs under kernel buffering or fragmentation.
Dually, `rpc_write_json_response` issued two `write()` calls ignoring partial
writes, truncating responses on slow-consuming clients.

### Remediation

1. **FP1**: added a thread-local per-request token cache (`s_req_auth`) keyed
   by the token string. `req_auth_ensure` parses the token once via
   `miku_token_verify_ex` (extracting both uid and platform); the four calling
   functions read from the cache instead of re-verifying. The HTTP server
   dispatches handlers sequentially in its epoll thread, so the thread-local is
   safe; the token is copied into TLS (no dangling pointer). **Net: 4×→1×
   HMAC per authenticated request.** Zero handler or call-site changes.
2. **FP2**: changed `miku_msggw_on_op_fn` to accept the parsed
   `miku_json_val_t *data` directly instead of `const char *payload, size_t
   len`. `read_client_frames` passes the already-parsed `data` subtree (or the
   full envelope `j` when `data` is absent); each handler case uses it directly.
   **Eliminates one `miku_json_stringify` + one `miku_json_parse` per WS
   message.** Net code reduction (the stringify/parse scaffolding was larger
   than the direct-pass alternative).
3. **FP3**: added `read_full` / `write_full` loop-until-complete helpers
   (EINTR-safe). Header (16 B) and length (4 B) reads now use `read_full`;
   payload read already looped. Response writes use `write_full`. Added
   `SO_RCVTIMEO` + `SO_SNDTIMEO` (5 s) on accepted RPC fds so a stuck client
   cannot stall the single-threaded accept+dispatch loop indefinitely.

### Deliberate deferrals (updated)

- **SP3 / scheduler `ready_entry_t`**: confirmed the coroutine scheduler is
  **test-only** (`tests/test_runtime.c` is the sole caller; no production
  binary uses it). The threadpool is production-reachable only via the webhook
  subsystem (async, low-frequency). Both malloc deferrals stand.
- **RPC full epoll/threadpool refactor**: the service layer has **zero locks**
  (`src/services/` — no mutex, spinlock, or atomic), so concurrent dispatch
  would corrupt state. A threadpool-dispatch model would require adding locks
  to every service first. Out of scope; the accept-queue drain (TP4) +
  deadlines (FP3) address the robustness gap without concurrency.

### Verification (fourth pass)

- `cmake --build build -j$(nproc)` — 0 warnings, 0 errors.
- `./build/bin/miku_tests` — 195/195 pass, exit 0.
- `ASAN_OPTIONS=detect_leaks=1 ./build-asan/bin/miku_tests` — 195/195 pass,
  exit 0, **zero leaks**, zero ASAN/UBSan runtime errors.
- WS gateway tests (`test_msggateway_opcode_reply`, `test_msggw_ws_deliver_msg`,
  `test_msggw_user_read_seq`, `test_ws_subscription_basic`, all 7 opcode
  handlers) pass. RPC tests (`test_rpc_server_e2e`, `test_rpc_client_call`,
  all 6 dispatch tests) pass.

## Fifth Pass (security + storage audit)

The fourth pass closed the hot-path CPU and RPC I/O issues. This pass audited
the previously-unreviewed foundation (crypto, hash, token), storage, and
protocol-parser layers for correctness and security defects.

### Findings

**FP4. Token signatures used non-cryptographic FNV-1a (CRITICAL SECURITY).**
`compute_sig` (`src/foundation/miku_token.c:79`) hashed the string
`uid:platform:ts:nonce:secret` with FNV-1a (`miku_fnv1a_64`) — a
non-cryptographic hash designed for hash tables, not authentication. The
secret was a **suffix in the hashed message**, not an HMAC key, so the
construction provided zero cryptographic guarantees: anyone with source
access could forge tokens for any user. Compounding this, the compile-time
default secret is the hardcoded string `"openIM123"`
(`miku_token.h:6`), used silently when `MIKU_TOKEN_SECRET` is unset.

**FP5. Per-request body strndup (minor performance).** `parse_body`
(`src/gateway/api/miku_api.c:347`) called `strndup(req->body.data,
req->body.len)` solely to null-terminate the body for
`miku_json_parse_str`, then freed the copy. The JSON parser already
exports `miku_json_parse(data, len)` which accepts a length — the copy
was unnecessary.

### Remediation

1. **FP4**: replaced `compute_sig` with **HMAC-SHA1** built on the existing
   `miku_sha1` primitive. The message is now `uid:platform:ts:nonce` (no
   secret); the secret is the HMAC key (padded or hashed per RFC 2104). The
   20-byte HMAC-SHA1 output is truncated to 64 bits to preserve the existing
   token format (`%016llx`). This is a non-breaking change — tokens created
   with the new construction verify with the new construction. Added a
   one-shot `MK_LOG_WARN` in `miku_token_default_secret` when the env var is
   unset, so operators are alerted at first token operation.
2. **FP5**: `parse_body` now calls `miku_json_parse(req->body.data,
   req->body.len)` directly, eliminating one `strndup` + `free` per API
   request.

### Observations (not fixed)

- **In-memory msg_store JSON construction** (`src/storage/miku_msg_store.c`):
  previously noted as unescaped; **now fixed** in the sixth pass (see FP7
  below). The in-memory result builders now use `json_escape_str`.
- **Session cache JSON** (`src/storage/miku_session_cache.c:39`):
  `snprintf(val, ..., "{\"token\":\"%s\",...}", token)` — the token value is
  not escaped. Low risk: the token is generated by `miku_token_create`
  (format `miku|...|sig`, no quotes). Not fixed.

### Verification (fifth pass)

- `cmake --build build -j$(nproc)` — 0 warnings, 0 errors.
- `./build/bin/miku_tests` — 195/195 pass, exit 0.
- `ASAN_OPTIONS=detect_leaks=1 ./build-asan/bin/miku_tests` — 195/195 pass,
  exit 0, **zero leaks**, zero ASAN/UBSan runtime errors.
- Token tests (`test_auth_user_token`, `test_token_revoke_force_logout`,
  `test_token_revoke_propagates_like_gateway`, `test_api_auth_login`,
  `test_mw_auth_*`) pass with the new HMAC construction.

## Sixth Pass (RPC client + NoSQL injection)

The fifth pass fixed the token crypto. This pass audited the RPC client
(every API→RPC call path) and the storage layer's MongoDB query construction.

### Findings

**FP6. RPC client short-read / partial-write (CORRECTNESS).**
`miku_rpc_call` (`src/protocol/miku_rpc_client.c`) used bare `write()` and
`read()` for the 16-byte header, 4-byte length, and payload — the same
defect fixed server-side in FP3. A short `write()` or `read()` (common under
network fragmentation or kernel buffering) would silently truncate the RPC
request or response, producing mysterious dispatch failures. Additionally,
no `SO_RCVTIMEO`/`SO_SNDTIMEO` was set on the connected fd, so an
unresponsive RPC server would block the API gateway's request thread
indefinitely.

**FP7. NoSQL injection in MongoDB filter construction (SECURITY).**
`miku_msg_store` interpolated user-controlled strings directly into MongoDB
JSON filter strings via `snprintf`:
- `find_by_conv`: `"{\"conversationID\":\"%s\",...}"` with user-provided
  `conversation_id`.
- `find_one`, `update_status`, `delete`: `"{\"msgID\":\"%s\"}"` with
  user-provided `msg_id` (the `clientMsgID` from delete/revoke API calls).
- `insert`: the full document with `msg_id`, `conversation_id`, `sender_id`,
  `content`.

A crafted `msgID` like `x","$where":"1==1` would inject an arbitrary
predicate into the query, bypassing the intended document scoping. The
in-memory result builders (`find_by_conv` loop, `find_one` output) had the
same unescaped interpolation, producing malformed JSON when message content
contained quotes.

### Remediation

1. **FP6**: added `rpc_read_full` / `rpc_write_full` (EINTR-safe loop helpers,
   identical contract to the server-side `read_full`/`write_full`). All
   header, length, and payload I/O now uses the full-read/write helpers.
   Added `SO_RCVTIMEO` + `SO_SNDTIMEO` (5 s) on the connected fd.
2. **FP7**: added `json_escape_str` (escapes `"`, `\`, and control chars per
   RFC 8259 §7) and applied it to all 6 user-string interpolation sites in
   `miku_msg_store.c` (3 MongoDB filters, 1 insert document, 2 in-memory
   result builders). Enlarged the `item`/`doc`/`buf`/`filter` buffers to
   accommodate the worst-case 2× expansion from escaping.

## Twentieth Pass (`/loop` — JSON codec conformance + serializer throughput)

Passes 6–19 hardened individual `snprintf` JSON call sites one subsystem at a
time (msg store, session cache, webhook, split-deploy sync, offline push). This
pass audited the **codec itself** — `src/protocol/miku_json.c`, the single
serializer and parser behind every HTTP response, RPC payload, and WS frame —
and found it non-conformant with RFC 8259 in both directions.

### Findings

**TW1. Object keys serialised unescaped (CRITICAL).** `stringify_val`'s object
case emitted keys via `miku_str_printf(s, "\"%s\":", key)`. A key containing
`"`, `\`, or a control character therefore produced **malformed JSON from the
serializer itself**, defeating every per-call-site escape fix from passes 6–19
(those hardened raw `snprintf` builders, not the serializer). Keys are
user-controlled on a reachable path: `fill_read_seq_entry`
(`src/gateway/msggateway/miku_msggw_ws_ops.c:104`) calls
`miku_json_object_set(map, cid, entry)` with the client-supplied
`conversationID` as the key, so a crafted WS `GET_CONV_MAX_READ_SEQ` request
corrupts the reply frame.

**TW2. Control characters below 0x20 emitted raw (HIGH).** The string case
escaped only `" \ \n \r \t \b \f`; every other C0 byte (e.g. `0x01`, `0x1F`)
fell through to `default: miku_str_cat_len(s, p, 1)` and was written literally.
RFC 8259 §7 requires all of `U+0000`–`U+001F` to be escaped. Message content is
client-supplied and reaches this path on every send, so a single raw control
byte in a message body invalidated the whole response document.

**TW3. `\uXXXX` escapes never decoded (HIGH).** `decode_string`'s escape switch
had no `case 'u'`, so `\u0041` hit `default: result[j++] = p->src[i]` and
decoded to the literal five characters `u0041`. Every inbound API body, RPC
payload, and WS frame was affected — any client that escapes non-ASCII text
(the default for many JSON encoders) had its data silently corrupted. This also
blocked TW2's fix, since the serializer's `\u00XX` output would not have
round-tripped.

**TW4. Per-character append on the serialisation hot path (PERFORMANCE).** The
string case appended one byte at a time via `miku_str_cat_len(s, p, 1)`, and
each call ran a capacity check, a one-byte `memcpy`, and a NUL write — so an
N-byte string cost N of each. Keys additionally went through `miku_str_printf`,
which runs `vsnprintf` **twice** (once to measure, once to write), as did every
integer via `miku_str_printf(s, "%lld", ...)`.

**TW5. WS gateway replies bypass the serializer (MEDIUM).** Five reply/notify
sites built JSON with raw `snprintf` on user-controlled strings, so the TW1/TW2
serializer fixes do not cover them:
- `miku_msggw_ws_ops.c` — `conversationID` in the `GET_NEWEST_SEQ` reply and in
  the READ-receipt reply; `clientMsgID` + `serverMsgID` in the `SEND_MSG` reply
  (both come straight from the client via `miku_im_msg_from_json`).
- `miku_ws_subscription.c` — `userID` in the online/offline status notification
  (pass 10 established that user IDs may contain quotes).

**TW6. `-Wshadow` warning regression (LOW).** `webhook_fire_json`
(`src/gateway/api/miku_api.c:351`, added in pass 10) declared a local
`char ev[512]` that shadows its `miku_webhook_event_t ev` parameter. Behaviour
was correct (the scopes do not overlap), but it broke the repo's 0-warning
invariant under the project-wide `-Wshadow`.

### Remediation (performance-optimal ordering)

The serializer rewrite fixes TW1, TW2, and TW4 in one pass over the same code,
so it leads. TW3 must land with TW2 for the escaping to round-trip.

1. **TW3 first** (parser): added `case 'u'` to `decode_string` with
   `decode_hex4` + `encode_utf8` helpers, including UTF-16 surrogate-pair
   recombination. Lone surrogates and `\u0000` become U+FFFD (RFC 8259 §8.2
   permits substitution) because an embedded NUL cannot survive in the C
   strings the codebase stores. The output is always shorter than the `\u`
   escape it replaces (≤4 bytes for ≥6 source bytes), so the existing
   `malloc(raw_len + 1)` sizing stays correct — no allocation change.
2. **TW1 + TW2 + TW4** (serializer): extracted `stringify_str`, used for both
   string values and object keys, which closes the key-escaping hole and the
   C0 gap at once. It escapes per RFC 8259 §7 (`\u%04x` for the remaining
   control bytes) and **appends escape-free spans as single blocks** rather
   than per byte — the common case (no escapes at all) becomes one
   `miku_str_cat_len` for the whole string. Also replaced `miku_str_printf`
   with a stack `snprintf` + `miku_str_cat_len` for integers (2 `vsnprintf` →
   1 `snprintf`), and swapped the fixed one- and four-character literals
   (`{`, `}`, `[`, `]`, `,`, `:`, `null`, `true`, `false`) from `miku_str_cat`
   to `miku_str_cat_len` with a compile-time length, dropping a `strlen` per
   token.
3. **TW5**: `miku_json_escape_str` (the shared helper from pass 8) applied to
   all five WS sites; reply buffers enlarged to hold the worst-case 2×
   expansion (`conv[128]` → `econv[256]` with `resp[512]`).
4. **TW6**: renamed the local buffer to `esc_val`.
5. Tests: `test_json_stringify_escapes_keys`,
   `test_json_stringify_escapes_control_chars`,
   `test_json_parse_unicode_escape` (BMP, CJK, surrogate pair, lone surrogate,
   `\u0000`), `test_ws_subscription_notify_escape`.

### Measured impact

Release build (`-O3 -march=native -flto`), `bench_json_stringify`, median of 3:

| | before | after |
|---|---|---|
| JSON stringify | 1.77M ops/sec | **4.87M ops/sec** (2.8×) |
| JSON parse | 2.76M ops/sec | 2.68M ops/sec (within noise) |

Every HTTP response, RPC payload, and WS frame in the system goes through this
path, so the serialiser gain applies to all three gateways. The parse side adds
only one switch branch, and the `\u` decode path itself is new work rather than
a regression.

## Twenty-first Pass (`/loop` — WebSocket frame reader stream safety)

Pass 20 fixed the JSON codec that sits behind every response. This pass audited
the layer in front of it on the real-time path: `src/protocol/miku_websocket.c`,
the frame reader both the msggateway (`read_client_frames`) and the generic
`miku_ws_server` (`ws_handle_client`) drive. It is the first code an
unauthenticated peer reaches after the HTTP upgrade, and it was not stream-safe.

### Findings

**TW7. Oversized frames desynced the connection, then crashed it (CRITICAL,
remotely triggerable).** `miku_ws_frame_read` guarded the payload read with
`if (plen > 0 && plen < 1048576)` and then `return (int)plen` — so for a frame
declaring ≥ 1 MiB it **skipped the payload read but still reported success**.
Three consequences chained:
1. The declared payload bytes stayed in the socket, so the caller's next
   `read(fd, hdr, 2)` parsed *payload* as a frame header. One frame permanently
   desynced the connection, after which every opcode and length the server acted
   on was attacker-chosen.
2. `f->payload` stayed `NULL` while `f->payload_len` held the huge declared
   length. `read_client_frames` guards the TEXT case on `frame->payload`, but
   the PING branch does not: `miku_ws_send_pong(c->fd, frame->payload,
   frame->payload_len)` forwarded `(NULL, huge)`.
3. `ws_send_frame` bounded that with `if (len + 14 > sizeof(buf)) return -1` —
   which **wraps** for a large `len`, so the check passed. `miku_ws_frame_encode`
   then computed `need = hdr + plen`, wrapping again and passing its own
   `need > out_cap` check, and reached `memcpy(out + pos, f->payload, plen)`
   with a NULL source. A single oversized PING frame crashes the process.
   `ws_handle_client` has the same PING branch and runs **before any
   authentication**.

**TW8. Short reads desynced the connection (HIGH).** All four reads
(`hdr[2]`, the 2- and 8-byte extended lengths, `masking_key[4]`) treated a
short return as a hard error. Gateway client fds are non-blocking
(`miku_set_nonblocking(cfd)` in `on_listen_io`), so a frame header split across
TCP segments returns fewer bytes than requested; the function returned -1 with
the consumed bytes already gone from the stream. This is the same defect class
fixed for the RPC server in pass 4 (FP3) and the RPC client in pass 6 (FP6),
but the WebSocket path was never covered.

**TW9. 64-bit length arithmetic wrapped in the decoder (MEDIUM).**
`miku_ws_frame_decode`'s `if (pos + plen > len)` sums a `size_t` and a
peer-controlled `uint64_t`. A length near `UINT64_MAX` wraps to a small value
and passes the check. `malloc` then failed on the huge size so this was not
directly exploitable, but the bound was not actually being enforced, and the
decoder had no maximum frame size at all.

### Remediation (performance-optimal ordering)

The reader fix removes the attack's entry point, so it leads; the encoder and
decoder guards are defence in depth for the same class.

1. **`MK_WS_MAX_PAYLOAD` (1 MiB)** promoted from the magic number buried in the
   old size check to `miku_websocket.h`, so reader and decoder share one bound.
2. **TW7**: `miku_ws_frame_read` now rejects `plen > MK_WS_MAX_PAYLOAD` with -1
   *before* allocating or reading anything, and logs the rejection. Because an
   oversized frame can never be skipped without losing the stream, closing the
   connection is the only correct response. `payload_len` is now assigned only
   after the payload is fully read, so callers can never see a length without a
   matching buffer.
3. **TW8**: added `ws_read_full`, which loops over partial reads and `EINTR`.
   The frame boundary is the one place a caller legitimately has nothing to
   read, so it takes an `at_frame_start` flag: with zero bytes consumed there it
   returns immediately (mapped to -1, preserving the existing "no more frames"
   contract that `read_client_frames` and `ws_handle_client` already rely on,
   and keeping `rc == 0` meaning a valid empty frame). Once any byte of a frame
   has been consumed it `poll()`s for the remainder up to a 5 s deadline —
   matching the `SO_RCVTIMEO` deadline pass 4 gave the RPC server — so a stalled
   peer cannot hold the epoll thread indefinitely. The budget is a wall-clock
   deadline for the whole read rather than a per-wait allowance: a payload up to
   `MK_WS_MAX_PAYLOAD` legitimately arrives across many segments, so it needs to
   poll repeatedly without the deadline resetting or expiring early.
4. **TW9**: `miku_ws_frame_decode` rejects `plen > MK_WS_MAX_PAYLOAD` and tests
   the remaining input as `plen > len - pos` (`pos <= len` is already
   established by the preceding bounds checks, so no wrap). `ws_send_frame`
   compares `len > sizeof(buf) - 14`, and `miku_ws_frame_encode` computes the
   header size first and compares `plen > out_cap - hdr`; both replace sums that
   could wrap. `miku_ws_frame_encode` also rejects a non-zero `payload_len` with
   a `NULL` payload outright.
5. **`miku_ws_handshake`** rejects `accept_cap == 0`, which would have made
   `accept_cap - 1` wrap into the base64 encoder.
6. Tests: `test_ws_frame_oversized_rejected` (decoder rejection, encoder
   wrap, NULL-payload rejection), `test_ws_frame_read_oversized_no_desync`
   (socketpair end-to-end reproduction of the crash chain),
   `test_ws_frame_read_split_header` (a header and payload arriving in three
   separate segments decode as one frame), and
   `test_ws_frame_read_multi_segment_payload` (a 4 KiB payload dripped in five
   delayed chunks, which requires several poll waits and so covers the
   wall-clock deadline).
